## 2026-11-12：数值变化但OFFLINE的实机原因

实串口与ROS诊断证实健康帧约10Hz持续到达、`receive_age_s`约0.05s，但健康payload和帧头timestamp始终为0；`health_age_s`不断增长。OFFLINE表示健康快照无有效进展，不等于以太网/SSH/串口都断开。主机没有把重复发送或无效快照当作持续健康。

外部固件源码漏掉 `robot_health_init()` 启动调用；`robot_health_get_snapshot()` 原来在未初始化时直接返回void，SerialTask却继续序列化未初始化局部变量。抓到的44字节报文混有此前底盘调用留下的电压、状态和递增时间戳等栈内容，虽有正确CRC，字段并不可信。故不能把52588 words、65535计数、STARTUP或历史0x0007当真实故障；独立有效底盘消息报告的安全状态为FAULT=7。

修复已直接写入外部main/RobotHealth/SerialTask并在仓库保存[补丁](../firmware/README.md)，重新生成54,752字节固件到 `~/stm32_ota/ubuntu_20261112_health_init/LeArm.bin`，尚未刷写。完整链接检查新增启动初始化顺序门槛；未初始化路径新增回归测试。原54,624字节产物同样缺初始化，不用于此次修复。

显示端现将“健康快照年龄”“帧接收年龄”“link诊断年龄”分开，附健康schema和快照timestamp。桥诊断在持续收到冻结快照时附带 `health frames arriving but snapshot timestamp not advancing`。帧仍到达不会掩盖快照冻结。

未知值分两类：旧44字节协议没有固件ID、uptime、当前故障、任务心跳等扩展字段；即使44字节发送正常也不能凭空补齐。schema1新固件提供这些观测，但owner和Arm反馈query尚未实现，应继续UNKNOWN。修复并升级后要检查128字节消息、变化的资源timestamp、心跳valid mask及实际安全状态，不能要求所有字段都变成已知或绿色。

## 协议与真实数据范围

健康消息仍为协议v1消息0x83，原44字节前缀保留。扩展帧固定128字节，offset44的schema=1；C端显式小端编码，C++按字段解析，不依赖结构体布局。新桥支持旧44字节消息，旧固件没有的当前故障、心跳等显示UNKNOWN，不把历史锁存故障误当实时值。详细offset表见固件工程`docs/健康遥测.md`。

扩展上报：快照时间、最小空闲堆、5任务历史最小剩余栈、累计错误、当前故障/历史故障/最近故障时间、5任务心跳年龄及有效位、底盘样本年龄、I2C连续失败、命令年龄与有效性、机械臂活动状态、最近安全转换、运行时间和TX丢弃。任务顺序为Default、Chassis、Serial、Arm、Health。

当前固件没有可靠的机械臂反馈查询观测和控制权仲裁模型，`arm_last_query`与owner保留未知；不会把示例中的RASPBERRY_PI或last query=OK当实测事实。固件ID为构建标记，不冒充Git版本。uptime基于32位毫秒tick，会回绕；历史故障保存在RAM，一次运行内保留，不声称断电持久化。

## 诊断分项与判定

保留原`learm_serial_bridge`诊断，新增：

```text
learm/health/link
learm/health/chassis
learm/health/arm
learm/health/communication
learm/health/safety
learm/health/resources
learm/health/tasks
```

采用diagnostic_msgs/DiagnosticArray，可供终端或rqt_robot_monitor订阅。当前错误与历史计数分开；恢复不清历史证据，历史非零也不永久判当前ERROR。人工急停是受控安全状态，和软件故障分别展示；Arm空闲时不因未查询而ERROR。

桥按steady clock独立判断健康帧，不用底盘数据续命；重复发送同一个健康快照不能不断刷新健康年龄。超过health_stale_after_s为STALE，超过health_offline_after_s或物理断线为OFFLINE。收到恢复后的有效新快照才恢复。所有分项随健康数据过期降级，不能保留绿色OK。

监视器还会用本机monotonic clock检查桥诊断是否停止，并将桥报告的health_age_s加上本机等待时间。即使最后一条是OK，桥或STM32卡住也会降级；其他IMU诊断不能刷新健康链路。

任务deadline比较的是健康快照采样时的心跳年龄，不把100ms健康发送周期额外叠到50ms底盘任务deadline上。健康报文本身另有过期阈值。

## 编译与运行

### 树莓派端

```bash
cd ~/RosCar
git status --short
git pull --ff-only origin main
cd pi_ws
bash build.sh
```

本地`pi.env`设`BRIDGE_IMPL=cpp`，并保持原设备与实测TF。仅验收串口与底盘的阶段，先启动最小桥，不需要IMU/EKF/雷达：

```bash
bash start.sh bridge --dry-run
bash start.sh bridge
```

后续需要整套传感器与EKF时改用all，不能与bridge同时运行。Python回退桥暂不解析扩展健康消息，健康展示须使用cpp。

健康阈值在C++包`config/health.yaml`，包括健康STALE/OFFLINE、各任务deadline、最小堆、栈余量、底盘样本年龄。更改源码配置后重新构建并重启；独立bridge launch的params_file和组合launch的health_params_file可指定外部配置。参数只在启动读取，不声称支持动态重配置。固件安全监控的既有deadline不因ROS阈值改变。

### 上位机端

```bash
cd ~/RosCar
git status --short
git pull --ff-only origin main
cd host_ws
bash build.sh
bash start.sh health --dry-run
bash start.sh health
```

先按host_ws/README配置本地host.env的Domain/DDS。健康监视器不需要显示服务器，可以在普通终端运行。调整显示侧阈值：

```bash
bash start.sh health --ros-args -p stale_after_s:=0.5 -p offline_after_s:=2.0 -p refresh_hz:=5.0
```

参数应不小于正常通信抖动，并与桥的阈值协调；显示端可更保守，不能取消桥的过期状态。TTY实时重绘，重定向输出最多1Hz，避免日志刷屏。
